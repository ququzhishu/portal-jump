# Portal Jump 核心原理

这篇文档说明 Portal Jump 怎么切换分辨率和缩放，用到哪些 Win32 接口和厂商驱动接口，以及代码里为什么要做回读、重试和恢复。

写给要改这部分代码的人。只想用软件的话看 `使用说明.md`。

## 一句话概括

托盘每 2 秒扫一次进程列表，发现关联程序在跑，就切显示模式；切完回读确认，12 秒内继续盯着，防止被游戏改回去。

## 代码分层

| 层 | 文件 | 职责 |
|---|---|---|
| 硬件后端 | `DisplayConfigBackend.cs` | 调 Win32 的 `ChangeDisplaySettingsEx`，管 `DEVMODE` 结构布局 |
| 语义兼容 | `DisplayInfo.cs` | 保留旧 API 名字，把 `DEVMODE` 转成界面层用的形式 |
| 业务逻辑 | `Switcher.cs` | 选后端、切模式、回读校验、重试与恢复 |

`DisplayInfo` 是薄包装，真正干活的是 `DisplayConfigBackend`。留着它是因为界面层和测试工具都在用旧名字，改名代价大于收益。

## 分辨率怎么切

核心是一个 Win32 调用：

```csharp
ChangeDisplaySettingsExA(null, ref dm, IntPtr.Zero, CDS_UPDATEREGISTRY, IntPtr.Zero);
```

`dm` 是 `DEVMODE` 结构，填好目标宽高、刷新率、色深，调用它系统就切过去。

`DEVMODEA` 的布局必须精确，这是最容易踩的一处。它是 156 字节，不是 160。旧版在 `dmReserved2` 后面多写了一个 `dmReserved3`，把结构撑到 160 字节。`dmSize` 写 160 时系统只读前 156 字节，多数情况不出错，但这是明确的越界布局。现在按 `wingdi.h` 逐字段对齐。

返回值 0 不代表切换成功。`ChangeDisplaySettingsEx` 返回 `DISP_CHANGE_SUCCESSFUL` 时，模式可能根本没变，驱动忙的时候会假成功。所以 `Switcher.WaitForMode` 要轮询回读，确认宽高和刷新率都到位：

```csharp
while (waited < timeoutMs)
{
    DisplayConfigBackend.DEVMODE cur = DisplayConfigBackend.GetCurrentMode();
    if (cur.dmPelsWidth == w && cur.dmPelsHeight == h && cur.dmDisplayFrequency == hz)
        return true;
    Thread.Sleep(120);
    waited += 120;
}
```

缩放不能单独设。Windows 只在源尺寸不等于目标尺寸时才有缩放概念。先切分辨率、再单独设缩放，第二次调用会被驱动拒绝。所以缩放必须并进切模式那一次调用：`ApplyMode` 里先 `SetFixedOutput(ref dm, scaling)` 改好 `dmDisplayFixedOutput` 字段，再一次性提交。

分辨率回读成功不等于缩放已经落地。驱动常先切模式、过一会儿才写缩放，所以还得再等一次 `WaitForFixedOutput`。

## 缩放的三条通路

同样是「全屏铺满」，不同显卡走不同接口。

| 显卡 | 通路 | 原因 |
|---|---|---|
| NVIDIA | NVAPI（`NvapiBridge.cs`） | 驱动不认 Windows 原生的缩放字段 |
| AMD | ADLX（`AdlxBridge.cs`） | 官方驱动配置接口，能精确回读 |
| 其它 | Win32 原生（`ApplyMode`） | 通用兜底，功能受限 |

在 N 卡上，`dmDisplayFixedOutput` 写不进去：调用返回成功，回读永远是默认值。必须走 NVAPI，读回当前的显示路径数组，只替换主显示器的缩放字段，再调 `DisplayApi.SetDisplayConfig` 提交。

A 卡的情况类似但原因不同。ADLX 是 AMD 官方的配置库（`amdadlx64.dll`），能精确读回当前缩放模式，Win32 原生字段不算可靠。

两套桥接的加载方式不一样。NvAPIWrapper 是编译期引用，源码里有 `using NvAPIWrapper;`，所以 `NvAPIWrapper.dll` 必须和 exe 放一起，这也是 AMD 版不带这个文件的原因。ADLX 则在运行时用 `LoadLibraryW` 加载 `amdadlx64.dll`（AMD 驱动自带，在 System32 下），按 COM 风格的 vtable 调用。

识别到 A 卡时完全不碰 NVAPI，识别到 N 卡时也不会去加载 ADLX。

## 怎么选通路

`GpuExtensions.cs` 决定编译期能力，`Switcher.ProbeNativeScalingWritable` 决定运行期走哪条。

厂商识别读硬件 ID，不读显示名：

```
PCI\VEN_10DE&DEV_2803&...  →  NVIDIA
PCI\VEN_1002&...           →  AMD
PCI\VEN_8086&...           →  Intel
```

本机为了游戏画质改过系统显示的显卡型号，WMI 报 `GTX 1050 Ti`，实际是 `RTX 4060 Ti`。名字能改，`VEN_10DE` 改不掉。

`EnumDisplayDevicesA` 在某些时刻会返回空列表，一个适配器都没置 `ATTACHED_TO_DESKTOP` 标志，比如刚开机或虚拟显示驱动刚加载的时候。这时按 attached 判厂商会得到「未知」，接着误判该走 Win32 原生接口。v0.22 的修法是重试 3 轮、间隔 120ms，仍失败就放宽 `attached` 条件按硬件 ID 再取一次。

放宽条件不会引入错误识别：虚拟显示驱动（向日葵的 `Root\OrayIddDriver`）的 `DeviceID` 里没有 `VEN_` 段，本来就取不出厂商 ID。

## 切换流程

`Switcher.Apply` 是整个程序最长的函数，流程是这样：

1. `FindModes(w, h)` 拿到该分辨率下所有模式，按刷新率降序
2. 当前已经是目标分辨率，跳过模式切换，直接单独设缩放
3. 逐个模式尝试：`ApplyMode` 提交，`WaitForMode` 回读确认
4. 并了缩放的话，再 `WaitForFixedOutput` 等缩放落地
5. 失败按结果码决定重试还是放弃
6. 全部失败，恢复到进入循环前的模式

第 6 步是 v0.22 加的。旧版在缩放失败时用 `continue` 继续试下一个刷新率，结果一路 144 → 120 → 60 → 50 → 30 → 29 → 25 → 24 → 23Hz，最后停在最低档才报错。缩放失败跟刷新率无关，降频解决不了问题，只是把屏幕越弄越难受。

现在缩放回读不符就立刻中止，循环结束后主动恢复原模式。

另外，连续 3 个模式被驱动以 `DISP_CHANGE_BADMODE`（-2）拒绝时，判定该分辨率整体不可用、提前退出。原来遇到这种情况会把 11 个模式全试一遍，白等几秒。

## 自动切换怎么触发

`Program.cs` 里一个 `System.Windows.Forms.Timer`，间隔 2000ms，每次 tick 调 `MonitorTick`。

`FindRunningGame` 把预设的关联程序名建成大小写不敏感的字典，然后遍历 `Process.GetProcesses()`，第一个命中的就是目标预设。预设顺序即优先级。

用轮询而不是事件驱动，是因为进程创建事件（`WMI Win32_ProcessStartTrace` 或 ETW）在这台机器上不够可靠，而 2 秒延迟对这个场景够用。代价是极短命的进程可能漏掉。

## 看门狗

游戏启动后常会自己再改一次分辨率，引擎初始化时会设成配置文件里的值。我们切换的时间点可能比它早几百毫秒，于是刚切完就被改回去。

`StartWatchdog` 在切换成功后启动，盯 6 个 tick（6 × 2 秒 = 12 秒）。每个 tick 检查当前模式是否还是目标值，不是就再切一次。最多纠正 3 次，防止和游戏无限拉锯。

## 配置热加载

`Config.cs` 负责解析 `presets.ini`。托盘为了避免每个 tick 都重新解析文件，`Program.ConfigStamp`（在 `Program.cs` 里）用文件修改时间做快速判断，没变就跳过。

配置文件优先放程序目录。程序装在 `C:\Program Files` 这类不可写位置时，自动改用 `%APPDATA%\PortalJump\presets.ini`。

## 自定义分辨率

NVIDIA 和 AMD 的创建流程不一样。

NVIDIA 是调驱动新建分辨率，画面立即切过去试用。内置 15 秒保护，不点保留就自动还原，防止驱动卡死后黑屏无法恢复。

AMD 只是把分辨率注册进驱动，不会立即切换。用户要回主界面在下拉框里选中它，再点应用。

这个差异写在 `CustomResolutionForm` 和 `CustomResolutionWindowAmd` 两套界面里。

## 界面为什么有两套

项目从 WinForms 迁到 WPF，两套并存。

`PortalJump.exe` 自带 WinForms 界面（`SettingsForm.cs` + `UiKit.cs`）。`PortalJump.UI.exe` 是独立的 WPF 界面进程（`src-ui/`）。

`Program.LaunchUi` 的逻辑是：`PortalJump.UI.exe` 存在就优先启动它，不存在才回退到内置界面。

所以改界面时先确认改的是哪一套。只改 `UiKit.cs` 而运行目录里有 `UI.exe`，用户看到的界面不会变。这个坑踩过一次，症状是改了代码但界面没变。

## 调试手段

强制指定缩放后端，排错时用：

```powershell
$env:PORTALJUMP_SCALING_BACKEND = "win32"   # 或 "nvapi"
```

程序目录的 `portal-jump.log` 记录每次切换尝试的模式、返回码和回读结果。

`PortalJump.exe selftest quiet` 生成 `portal-jump-selftest.txt`，包含厂商识别、NVAPI 状态、当前模式、缩放通路。

想判断某个模式能不能用但不实际切换，用 `DisplayConfigBackend.TestMode`，它传 `CDS_TEST` 标志给系统。
