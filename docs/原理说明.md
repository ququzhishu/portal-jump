# Portal Jump 核心原理

这篇文档说明 Portal Jump 是怎么切换分辨率的，以及为什么它的实现比"直接调一个 API"复杂得多。

面向想改代码或判断某个 bug 该在哪一层修的人。只想用软件的话看 `使用说明.md`。

## 一句话概括

托盘每 2 秒扫一次进程列表，发现关联程序在跑，就调三层接口里的合适那层，把显示模式切过去；切完回读确认，12 秒内还会盯着，防止被游戏改回去。

## 三个抽象层

代码分成三层，从下往上。

| 层 | 文件 | 职责 |
|---|---|---|
| 硬件后端层 | `DisplayConfigBackend.cs` | 直接调 Win32 的 `ChangeDisplaySettingsEx`，管 `DEVMODE` 结构布局 |
| 语义兼容层 | `DisplayInfo.cs` | 保留旧 API 名字，把 `DEVMODE` 转成界面层友好的形式 |
| 业务逻辑层 | `Switcher.cs` | 选后端、切模式、回读校验、重试与恢复 |

`DisplayInfo` 只是薄包装，真正干活的是 `DisplayConfigBackend`。留着它是因为界面层和测试工具都在用它的旧名字，改名代价大于收益。

## 分辨率怎么切

核心就一个 Win32 调用：

```csharp
ChangeDisplaySettingsExA(null, ref dm, IntPtr.Zero, CDS_UPDATEREGISTRY, IntPtr.Zero);
```

`dm` 是 `DEVMODE` 结构，填好目标宽高、刷新率、色深，调用它，系统就切过去。

看起来简单，实际有三个坑。

坑一：结构体布局必须精确。 `DEVMODEA` 是 156 字节，不是 160。旧版在 `dmReserved2` 后面多写了一个 `dmReserved3`，把结构撑到 160 字节。虽然 `dmSize` 写 160 时系统只读前 156 字节、多数情况不出错，但这是明确的越界布局。现在按 `wingdi.h` 逐字段对齐，实测 156 字节。

坑二：返回值 0 不代表切换成功。 `ChangeDisplaySettingsEx` 返回 `DISP_CHANGE_SUCCESSFUL`（0）时，模式可能根本没变。驱动忙的时候会"假成功"。

所以 `Switcher.WaitForMode` 会轮询回读，确认宽高和刷新率都真的到位：

```csharp
while (waited < timeoutMs)
{
    DisplayConfigBackend.DEVMODE cur = DisplayConfigBackend.GetCurrentMode();
    if (cur.dmPelsWidth == w && cur.dmPelsHeight == h && cur.dmDisplayFrequency == hz)
        return true;
    Thread.Sleep(120);
    waited += 120;
}
```

坑三：缩放不能单独设。 Windows 只在"源尺寸不等于目标尺寸"时才有缩放概念。先切分辨率、再单独设缩放，第二次调用会被驱动拒绝。

所以缩放必须并进切模式那一次调用。`ApplyMode` 里先 `SetFixedOutput(ref dm, scaling)` 改好 `dmDisplayFixedOutput` 字段，再一次性提交。

## 缩放的三条通路

同样是"全屏铺满"，不同显卡走完全不同的接口。这是本项目最麻烦的部分。

| 显卡 | 通路 | 为什么 |
|---|---|---|
| NVIDIA | NVAPI（`NvapiBridge.cs`） | 驱动不认 Windows 原生的缩放字段 |
| AMD | ADLX（`AdlxBridge.cs`） | 官方驱动配置接口，精确且可回读 |
| NVIDIA / AMD / Intel | Win32 原生（`ApplyMode`） | 通用兜底，功能受限 |

NVIDIA 为什么要专用接口。 `dmDisplayFixedOutput` 在 N 卡上写不进去：调用返回成功，回读永远是默认值。必须走 NVAPI：读回当前的显示路径数组，只替换主显示器的缩放字段，再调 `DisplayApi.SetDisplayConfig` 提交。

AMD 为什么要专用接口。 ADLX 是 AMD 官方的配置库（`amdadlx64.dll`），能精确读回当前缩放模式。Win32 原生字段在 A 卡上也不完全可靠。

两套桥接的加载方式不同。NvAPIWrapper 是编译期引用，源码里 `using NvAPIWrapper;`，所以 `NvAPIWrapper.dll` 必须和 exe 放在一起，这也是 AMD 版不带这个 DLL 的原因。ADLX 则是运行时用 `LoadLibraryW` 加载 `amdadlx64.dll`（AMD 驱动自带，位于 System32），再按 COM 风格的 vtable 调用。识别到 A 卡时完全不碰 NVAPI，识别到 N 卡时也不会去加载 ADLX。

## 怎么选通路

`GpuExtensions.cs` 决定编译期能力，`Switcher.ProbeNativeScalingWritable` 决定运行期通路。

厂商识别走硬件 ID，不看显示名：

```
PCI\VEN_10DE&DEV_2803&...  →  NVIDIA
PCI\VEN_1002&...           →  AMD
PCI\VEN_8086&...           →  Intel
```

为什么不用显示名：本机为了游戏画质改过系统显示的显卡型号，WMI 报 `GTX 1050 Ti`，真实是 `RTX 4060 Ti`。名字会骗人，`VEN_10DE` 这种硬件 ID 改不掉。

这里有个已知的脆弱点。 `EnumDisplayDevicesA` 在某些时刻（比如刚开机、虚拟显示驱动刚加载）会返回空列表，一个适配器都没置 `ATTACHED_TO_DESKTOP` 标志。这时按 attached 判断厂商会得到"未知"，进而误判该走 Win32 原生接口。

v0.22 的修法是加重试（3 轮，间隔 120ms），仍失败就把 `attached` 条件放宽，按硬件 ID 再取一次。虚拟显示驱动（向日葵的 `Root\OrayIddDriver`）的 `DeviceID` 里没有 `VEN_` 段，放宽条件不会把它误认成显卡。

## 切换流程

`Switcher.Apply` 是整个程序最复杂的函数。完整流程：

1. `FindModes(w, h)` 拿到该分辨率下所有模式，按刷新率降序
2. 若当前已经是目标分辨率，跳过模式切换，直接单独设缩放
3. 逐个模式尝试：`ApplyMode` 提交，`WaitForMode` 回读确认
4. 若并了缩放，再 `WaitForFixedOutput` 等缩放落地
5. 失败则按结果码决定重试还是放弃
6. 全部失败，恢复到进入循环前的模式

第 6 步是 v0.22 加的。旧版在缩放失败时用 `continue` 继续试下一个刷新率，结果一路 144 → 120 → 60 → 50 → 30 → 29 → 25 → 24 → 23Hz，最后停在最低档才报错。缩放失败跟刷新率无关，降频解决不了问题，只会把屏幕弄得很难受。

现在的做法是：缩放回读不符立刻中止，循环结束后主动恢复原模式。

另外连续 3 个模式被驱动以 `DISP_CHANGE_BADMODE`（-2）拒绝时，判定该分辨率整体不可用，提前退出。这条是为了避免空转：原来会把 11 个模式全试一遍，白等几秒。

## 自动切换怎么触发

`Program.cs` 里一个 `System.Windows.Forms.Timer`，间隔 2000ms，每次 tick 调 `MonitorTick`。

`FindRunningGame` 把预设的关联程序名建成字典（大小写不敏感），然后 `Process.GetProcesses()` 遍历一遍，第一个命中的就是目标预设。预设顺序即优先级。

轮询而不是事件驱动，原因是进程创建事件（`WMI Win32_ProcessStartTrace` 或 ETW）在这台机器上不够可靠，而且轮询 2 秒的延迟对"打开游戏自动切分辨率"这个场景完全够用。代价是极短命的进程可能漏掉。

## 看门狗

游戏启动后常会自己再改一次分辨率（引擎初始化时会设成配置文件里的值）。我们切换的时间点可能比它早几百毫秒，于是刚切完就被改回去。

`StartWatchdog` 在切换成功后启动，盯 6 个 tick（6 × 2 秒 = 12 秒）。每 tick 检查当前模式是否还是目标值，不是就再切一次。最多纠正 3 次，防止和游戏无限拉锯。

## 配置热加载

`Config.cs` 负责解析 `presets.ini`。托盘为了避免每个 tick 都重新解析文件，`Program.ConfigStamp`（在 `Program.cs` 里）用文件修改时间做快速判断，没变就跳过。

配置文件优先放程序目录。若程序装在 `C:\Program Files` 这类不可写位置，自动改用 `%APPDATA%\PortalJump\presets.ini`。

## 自定义分辨率

NVIDIA 和 AMD 的创建流程完全不同。

NVIDIA：调驱动新建分辨率，画面会立即切过去试用。内置 15 秒保护，不点"保留"就自动还原，防止驱动卡死后黑屏无法恢复。

AMD：只是把分辨率注册进驱动，不会立即切换。用户需要回主界面在下拉框里选中它，再点"应用"。

这个差异写在 `CustomResolutionForm` 和 `CustomResolutionWindowAmd` 两套界面里。

## 界面为什么有两套

项目从 WinForms 迁到 WPF，两套界面并存。

`PortalJump.exe` 自带 WinForms 界面（`SettingsForm.cs` + `UiKit.cs`）。`PortalJump.UI.exe` 是独立的 WPF 界面进程（`src-ui/`）。

`Program.LaunchUi` 的逻辑是：`PortalJump.UI.exe` 存在就优先启动它，不存在才回退到内置界面。

改界面时必须清楚改的是哪一套。 只改 `UiKit.cs` 而运行目录里有 `UI.exe`，用户看到的界面不会变。这个坑踩过一次，症状是"改了代码但界面没变"。

## 调试手段

强制指定缩放后端，排错时用：

```powershell
$env:PORTALJUMP_SCALING_BACKEND = "win32"   # 或 "nvapi"
```

程序目录的 `portal-jump.log` 记录每次切换尝试的模式、返回码和回读结果。

`PortalJump.exe selftest quiet` 生成 `portal-jump-selftest.txt`，包含厂商识别、NVAPI 状态、当前模式、缩放通路。

想判断某个模式能否接受但不实际切换，用 `DisplayConfigBackend.TestMode`，它传 `CDS_TEST` 标志给系统。
